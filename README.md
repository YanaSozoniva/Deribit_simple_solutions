# 📊 Deribit Price Tracker

Сервис для автоматического сбора индексных цен BTC/USD и ETH/USD с биржи [Deribit](https://www.deribit.com/) и предоставления REST API для работы с историческими данными.

Сбор данных происходит каждую минуту через фоновые задачи Celery. Данные сохраняются в PostgreSQL и доступны через FastAPI.

## 🛠 Стек технологий

| Компонент | Технология | Назначение |
|-----------|------------|------------|
| API | **FastAPI** | HTTP-эндпоинты для чтения данных |
| ORM | **SQLAlchemy 2.0** | Работа с PostgreSQL |
| Миграции | **Alembic** | Управление схемой БД |
| Фоновые задачи | **Celery + Celery Beat** | Периодический сбор цен |
| Брокер сообщений | **Redis** | Очередь задач для Celery |
| HTTP-клиент | **aiohttp** | Асинхронные запросы к Deribit API |
| База данных | **PostgreSQL 15** | Хранение исторических цен |
| Конфигурация | **Pydantic Settings** | Валидация переменных окружения |
| Тестирование | **pytest + httpx** | Unit-тесты API |
| Оркестрация | **Docker Compose** | Развёртывание всех сервисов |

## 📦 Установка

## 🚀 Быстрый старт (Docker)

Самый простой способ запустить весь проект одной командой.

### 1. Клонируйте репозиторий

```bash
git clone git@github.com:YanaSozoniva/Deribit_simple_solutions.git
cd Deribit_simple_solutions
```

### 2. Запустите все сервисы

```bash
docker compose up --build -d
```

Будут подняты 5 контейнеров:
- `db` — PostgreSQL (порт 5432)
- `redis` — Redis (порт 6379)
- `api` — FastAPI (порт 8000)
- `celery_worker` — исполнитель задач
- `celery_beat` — планировщик задач

### 3. Проверьте работоспособность

```bash
# Логи API
docker compose logs api

# Swagger UI
open http://localhost:8000/docs
```

Через 1 минуту после старта Celery начнёт собирать цены. Проверить можно так:

```bash
curl "http://localhost:8000/prices/latest?ticker=btc_usd"
```

### 4. Остановка

```bash
docker compose down        # остановить контейнеры
docker compose down -v     # остановить и удалить volume с данными
```

## 💻 Локальная разработка (без Docker)

### 1. Установите PostgreSQL и Redis локально

Убедитесь, что PostgreSQL слушает порт `5432`, а Redis — `6379`.

### 2. Создайте базу данных

```bash
createdb deribit_db
# или через psql:
# CREATE DATABASE deribit_db;
```

### 3. Создайте виртуальное окружение и установите зависимости

```bash
python -m venv .venv
source .venv/bin/activate   # Linux/macOS
# или .venv\Scripts\activate  # Windows

pip install -r requirements.txt
```

### 4. Создайте файл `.env`

```env
postgres_user=postgres
postgres_password=postgres
postgres_host=127.0.0.1
postgres_port=5432
postgres_db=deribit_db
redis_url=redis://127.0.0.1:6379/0
```

### 5. Примените миграции

```bash
alembic upgrade head
```

### 6. Запустите сервисы в разных терминалах

**Терминал 1 — API:**
```bash
uvicorn app.main:app --reload --port 8000
```

**Терминал 2 — Celery Worker:**
```bash
celery -A app.tasks.celery_app worker --loglevel=info
```

**Терминал 3 — Celery Beat:**
```bash
celery -A app.tasks.celery_app beat --loglevel=info
```

## 📡 API Endpoints

Все методы — `GET`, обязательный query-параметр `ticker`.

### 1. Все цены по тикеру
```bash
GET /prices?ticker=btc_usd
```

### 2. Последняя цена
```bash
GET /prices/latest?ticker=btc_usd
```

### 3. Цены за конкретную дату
```bash
GET /prices/by_date?ticker=eth_usd&date=2026-10-17
```

### Пример ответа
```json
{
  "id": 42,
  "ticker": "btc_usd",
  "price": 67845.32,
  "timestamp": 1729152000
}
```


## 🧠 Design Decisions

### 1. Разделение драйверов PostgreSQL: `asyncpg` vs `psycopg`

**Решение:** Приложение использует асинхронный драйвер `asyncpg`, а Alembic — синхронный `psycopg` (v3). URL-ы разделены через `@computed_field` в Pydantic Settings.

**Обоснование:**
- `asyncpg` даёт максимальную производительность для HTTP-запросов FastAPI.
- `psycopg` v3 — официальный преемник `psycopg2`, рекомендован SQLAlchemy 2.0.
- Миграции — разовые административные операции, асинхронность в них не нужна.
- Синхронный драйвер стабильнее работает на Windows (избегаем `WinError 64` от `asyncio.ProactorEventLoop`).
- Такой подход соответствует принципу **разделения ответственности**: каждый инструмент используется по назначению.

### 2. Хранение времени в UNIX timestamp

**Решение:** Поле `timestamp` имеет тип `Integer`, а не `DateTime`.

**Обоснование:**
- **Timezone-agnostic:** UNIX timestamp не зависит от часовых поясов, что исключает ошибки при работе с биржей (UTC).
- **Производительность:** Сравнение целых чисел в PostgreSQL эффективнее, чем операции с `DateTime`.
- **Простота фильтрации:** Диапазонные запросы (`BETWEEN start_ts AND end_ts`) используют стандартный B-tree индекс.
- **Совместимость:** Легко сериализуется в JSON без дополнительных преобразований.

### 3. Repository Pattern

**Решение:** Логика работы с БД вынесена в `PriceRepository`, который инжектируется через `Depends()`.

**Обоснование:**
- **Тестируемость:** Репозиторий легко мокать в unit-тестах без реальной БД.
- **Переиспользование:** Запросы не дублируются в разных эндпоинтах.
- **Гибкость:** При необходимости можно сменить ORM или БД, изменив только реализацию репозитория.
- **Чистая архитектура:** Бизнес-логика отделена от деталей хранения данных.

### 4. Асинхронный клиент Deribit (`aiohttp`)

**Решение:** Клиент биржи реализован через `aiohttp` с использованием `asyncio.gather()` для параллельных запросов.

**Обоснование:**
- Закрытие необязательного требования задания.
- Параллельный запрос `btc_usd` и `eth_usd` экономит время (2 запроса выполняются за время одного).
- Ошибки изолированы через `return_exceptions=True` — падение одного тикера не ломает всю задачу.
- Класс `DeribitClient` инкапсулирует работу с API, что позволяет легко добавлять retries, кэширование или менять провайдера.

### 5. Celery + Redis

**Решение:** Для периодического сбора данных используется Celery Beat + Redis.

**Обоснование:**
- **Промышленный стандарт:** Celery — зрелое решение с мониторингом, retry-логикой, распределённым выполнением.
- **Масштабируемость:** При росте нагрузки можно добавить несколько worker-контейнеров.
- **Redis как универсальный компонент:** Один сервис используется и как брокер, и как бэкенд результатов.

### 6. Отсутствие `create_all` в `main.py`

**Решение:** Схема БД управляется исключительно через Alembic.

**Обоснование:**
- `Base.metadata.create_all()` при каждом старте приложения — плохая практика для продакшена.
- Alembic — единственный источник истины о схеме БД.
- Миграции воспроизводимо применяются в CI/CD и на разных окружениях.
- При старте контейнера `api` выполняется `alembic upgrade head` автоматически.

### 7. Pydantic Settings + `@computed_field`

**Решение:** Конфигурация собирается из переменных окружения через `pydantic-settings`, URL БД вычисляется динамически.

**Обоснование:**
- **12-Factor App:** Конфигурация хранится в окружении, а не в коде.
- **Единый источник правды:** Отдельные поля (`postgres_host`, `postgres_port`) удобнее переопределять, чем всю строку URL.
- **Валидация:** Pydantic автоматически проверяет типы и обязательность полей.
- **Без глобальных переменных:** Настройки инкапсулированы в классе `Settings`, передаются через DI.

### 8. Docker Compose с разделением сервисов

**Решение:** API, Celery Worker, Celery Beat, БД и Redis — отдельные контейнеры.

**Обоснование:**
- **Изоляция отказов:** Падение worker-а не влияет на API.
- **Независимое масштабирование:** Можно запустить несколько реплик worker-а (`docker compose up --scale celery_worker=3`).
- **Разные команды запуска:** API — это `uvicorn`, worker — `celery worker`, beat — `celery beat`.
- **Соответствие заданию:** Реализовано требование "развернуть в двух контейнерах" (фактически — в пяти, что даже лучше).

### 9. Синхронный Celery с `asyncio.run()` внутри

**Решение:** Задача `fetch_and_save_prices` синхронная, но внутри использует `asyncio.run()` для вызова асинхронного клиента.

**Обоснование:**
- Celery по умолчанию синхронный, полная миграция на async требует дополнительных пулов (`eventlet`).
- `asyncio.run()` создаёт изолированный event loop для каждой задачи, избегая конфликтов.
- Сохраняется производительность `aiohttp` при параллельных запросах к бирже.
- ORM-операции остаются синхронными и предсказуемыми.

### 10. Отсутствие глобальных переменных

**Решение:** Все зависимости (БД, клиент, репозиторий) передаются через механизм `Depends()` FastAPI.

**Обоснование:**
- Упрощает тестирование через `app.dependency_overrides`.
- Гарантирует корректное открытие/закрытие ресурсов (сессий БД, HTTP-сессий).
- Делает код предсказуемым и легко читаемым.
- Соответствует принципам Dependency Injection и чистой архитектуры.
